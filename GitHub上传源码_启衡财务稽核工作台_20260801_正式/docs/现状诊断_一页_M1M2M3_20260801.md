# 启衡财务稽核工作台：现状诊断（一页）

## 业务问题

费用报销审核需要在报销单、费用行、原票、审批/特批、发票台账、员工与差旅标准之间交叉核对。人工在多个页面间切换，难以稳定保留“为什么判错、依据在哪里、谁最终确认”的证据链。月结前的发票台账又与逐单报销审核不同：它需要看全量重复票据、票面字段和供应商主数据风险。

## 根因

1. 证据分散：单据字段、审批链、原票与台账不在同一操作页。
2. OCR 有天然盲区：电子客票通常没有购买方/税号；不能因 OCR 空白自动放行，也不能把 OCR 误读直接当最终裁决。
3. ERP 写回存在覆盖风险：已有财务意见时继续写入会形成相互矛盾的审核记录。
4. 台账稽核被误当成报销审核：23,461 条是历史发票记录，不是 23,461 张报销单；M3 需要任务分派和闭环，而非伪造 ERP 回写。

## 解决方案

工作台按“原票 > 已确认台账 > ERP 字段 > OCR > 模型建议”组织证据：

- M2 在同页呈现单据、费用明细、审批/特批、原票与可解释初审意见；财务确认、驳回、补材或人工校准后才进入写回队列。
- OCR 字段纠正与结论改判保存为本地人工确认样本；纠正后重新执行整单规则，不自动修改全局制度或模型。
- 写回前与 POST 前各读一次 ERP 既有审核意见；只有 ERP 空意见允许写入，已有相同或冲突意见均转 ERP 人工处理。
- M3 全量只读扫描发票台账，输出重复票据、抬头/税号/税率待核查任务、负责人和处理备注；不回传 ERP。

## 交付与边界

EXE 在新电脑首次输入 API 地址与本环境 API Key 后，实时从 API 拉取数据；历史运行包、人工样本和评测材料仅作参考，不替代当前数据。演示 HTML 明确使用虚拟数据。当前正式交付范围为 M1-M3；M4 为历史扩展原型，不列入本次 EXE、权限或提交 JSON。

## 验收重点

最终隔离环境验收应证明：300 张待审单重新拉取并生成完整结果；BX202606-5693 类电子客票台账不一致转人工复核；校准后整单重判；M3 全量扫描；一次人工确认后的安全写回及一次既有意见冲突拦截；官方 `validate-submission.mjs` 无 error。
