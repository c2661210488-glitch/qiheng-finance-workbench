# 启衡财务稽核工作台：整改历程、交付架构与验证清单

更新时间：2026-08-01  
本文件是当前工程的事实清单，不把未运行的检查写成“已通过”。本轮交付范围为 M1（登录与连接）、M2（费用报销审核和人工闭环）、M3（发票台账稽核）；M4 不作为本轮验收功能。

## 1. 交付目标与数据边界

EXE 不是固定结果演示器。启动后先输入导师 ERP 的 API 地址与 API Key；连接成功后只读拉取该环境当前的待审报销单、费用行、附件、审批记录、主数据和发票台账，再在本地生成新的初审建议。

- M2 只有财务人工确认后，才调用 `POST /v1/expense-claims/{id}/review` 写入审核意见；不得改变单据状态、支付或删除数据。
- 写回前必须读取既有审核意见：同意见跳过，不同意见标为冲突，不能覆盖。
- M3 只读拉取全量发票台账并形成稽核任务、负责人和本地备注；不得伪造“已回写 ERP”。
- 本地结果/缓存仅用于任务历史和断网恢复，必须显示来源、生成时间和规则版本；刷新或重新拉取后必须以 ERP 当前数据为准。
- `submission.json`、公开样本对比、300 单运行日志属于比赛验收证据包，不应替代 EXE 对新 ERP 的重新拉取与重新判责。

本轮进一步收紧：主题版工作台启动时不再把 `analysisCache` 或 M3 缓存加载为当前队列/当前稽核结果；选择单据后每次重新读取 ERP 单据、审批、附件和台账，再生成本次建议。缓存只保留给审计包与人工确认样本库，不能作为实时数据源。

写回前会进行两次保护：预检读取既有意见；点击确认后、实际 POST 前再次读取。只要 ERP 已有任何审核意见（无论相同或不同），系统都跳过该单并标记为需在 ERP 人工处理。写回还会先校验 `expense:review` 权限。

## 3. 已发现并修正的关键问题

### 3.1 电子客票/车票被错误建议通过

**问题**：`LONG_TRANSPORT` 被排除在购买方/税号核验之外。车票 OCR 无法读出购买方时，代码会把它视为可放行，尽管关联 ERP 发票台账的购买方或税号不正确。

**涉及单据**：`BX202606-5693`。该单必须以关联 ERP 台账核对，不能因为电子客票本身没有增值税发票的购买方字段而自动通过。

**修正位置**：`src/reviewer.py`。

**新规则**：

1. 普通增值税发票：原票/人工确认值优先，再与台账、ERP 和 OCR 对比。
2. `LONG_TRANSPORT`（电子客票、火车票、机票等）：票面通常没有购买方/税号，关联 ERP 台账是必核来源。
3. 台账购买方或税号缺失：`FLAG`，转二次人工复审。
4. 台账购买方或税号与公司主数据不一致：`FLAG`，展示台账实际值、正确值和复审原因；不得 `APPROVE`。
5. 财务人工确认台账实际值不正确：`REJECT`，保留人工依据和字段值。

本地合成回归已完成：台账不一致、台账缺失均为 `FLAG`；人工确认错误购买方为 `REJECT`。由于当前凭据库没有可用 API Key，`BX202606-5693` 的真实 ERP 回归尚未完成，恢复有效 Key 后必须执行。

### 3.2 OCR 无法读取时跳过了后续台账判断

**问题**：`src/reviewer.py` 遇到 OCR 为空会 `continue`，导致关联台账、人工纠正和规则均未执行。

**修正**：OCR 失败保留空提取对象和“附件无法读取”复核标记，继续执行 ERP 台账判断。因而“图片读不出”不会成为自动通过的理由。

### 3.3 “保存校准并重新判责本单”不能纠正车票

**问题**：校准页强制填写金额；购买方、税号默认预填为公司正确值，既不能表达台账的实际错误值，也容易形成无意义覆盖。

**修正位置**：`desktop_finance_workbench.py`。

- 金额变为可留空，仅在金额纠正时填写。
- 购买方/税号默认留空；发票填写原票实际值，电子客票/车票填写 ERP 台账实际值。
- 至少需填一个校准字段和校准依据。
- 保存后将该单全部已确认字段传给 `analyze_one()`，重新下载/读取、OCR、查台账、查审批、查重复票并执行完整 `review_claim()`；结果更新到当前队列，而不是只改一个标签。

### 3.4 校准结果会被后续批审覆盖；数据源冲突被静默放行

**问题 A**：批量审核此前未传入已保存的本地校准字段，因此“保存校准并重判”后再次一键审核，可能回到未经校准的 OCR 结论。

**修正**：根目录工作台和当前主题版构建入口均统一从本地人工确认样本库读取该单 `ocr_overrides`；单张重审、校准后重审和一键审核全部使用同一份已确认字段。

**问题 B**：普通发票在原票/OCR 显示公司正确、ERP 台账购买方或税号却错误时，旧逻辑可能直接通过。

**修正**：原票/人工确认字段与 ERP 台账存在购买方或税号冲突时，统一 `FLAG` 并进入二次人工复审；系统既不自动批准，也不自动覆盖 ERP。

## 4. 必须执行的真实回归（恢复 API Key 后）

以下每项均为只读，除最后一项明确人工确认后写回：

1. 登录导师 ERP，检查 API 地址、Key 和最小读取权限。
2. 打开 `BX202606-5693`，记录关联费用行、电子客票附件、ERP 台账购买方/税号和公司主数据。
3. 点击“初审当前单据”：若台账不一致，结果必须是“待人工复审”，且证据显示实际值、正确值、来源为 ERP 台账和下一步。
4. 在人工校准中填写车票关联台账的实际购买方/税号和依据，保存并重新判责：结果必须更新；若人工确认不符，必须为“建议驳回”。
5. 对普通增值税发票分别验证：OCR 为空、OCR 与台账冲突、台账错误、人工字段纠正、重复票、金额不符、缺审批、特批覆盖。
6. 运行 300 单一键审核，保存开始/结束时间、成功/失败数、APPROVE/REJECT/FLAG 数和失败原因。当前实际观测目标为约 25 分钟/300 单；不得将其等同为人工节省的全部时间。
7. 从“待人工复审”人工确认一条，执行写回前预检；已有不同意见必须显示冲突且不可覆盖。
8. M3 点击“读取全量发票，开始稽核”，核验只展示异常、可分配负责人和本地闭环，不发生 ERP 回写。

## 6. ROI 正确口径

财务部历史表中的人工平均处理时间约为 4.81 分钟/单。300 单纯人工基线约 24.1 小时。系统批处理约 25 分钟/300 单时，理论最大节省为约 23.6 小时/批，但只有在运行无人值守时才可将这 25 分钟视为非人工时间。

最终 ROI 必须记录：人工复核的单量与分钟数、写回冲突处理时间、运行与维护成本。不得使用“300 单节省 45 小时”这类超过人工基线的数字。
